# Memo - Harbour, as inherited vs as shipped

To: Head of platform engineering  
From: Kabir Singh Lamba  
Date: 13 September 2026

We inherited a demo that closed easy servicing cases. The eval was green even when behaviour changed. Platform would not put it behind the load balancer. Below is what I found and what I shipped.

**What was actually wrong.** The six complaints mostly came from the same gaps. There was no `/readyz`, and `/healthz` only returned `{"ok":true}`, so nothing could load-balance it. Model calls had no hard timeout, so a slow upstream hung a worker (and hung the checker). Spend was not capped in-process and not written on traces. `POST /run` ran the work again when the same idempotency key came twice. The eval suite was 40 offline cases; it stayed green if the system prompt disappeared or tool JSON was scrambled. Money tools trusted a sticky `customers.verified` flag from an earlier contact, and `cancel_autopay` did not require verify at all - that matches the audit row where money moved with no identity step. Pasted “SYSTEM:” / override text in the customer message could also become extra tool calls. The old loop even fed free-text tool notes back in as user turns.

**What it now guarantees.** My last full contract run is `results/contract_check.json`: 10/10, faults 100%, p95 902 ms on synthetic `/run`. Every model call still goes through `LLM_BASE_URL`. `/healthz` reports `APP_VERSION`. `/readyz` fails closed if the spend cap is garbage. Chat timeout is 8 s; a timeout is 504 and I do not retry that call. Cap is `MAX_SPEND_USD`. Same idempotency key and same input replay; different input is 409. Traces go to OTLP with tokens and `cost_usd`, and a span per backend tool (`execute_tool`). `make eval` writes `eval_report.json` at the repo root and goes red under the four published prompt regressions. Money tools, including cancel-autopay, need a successful `verify_identity` on this case, not a leftover DB flag. Overlay-only contact changes and extra waives are refused before they hit the audit log.

**What it still does not.** I have not scored the 60 held-out cases. 10/10 HTTP is not task-success. On the 180 published cases, live `gpt-4.1-mini-2025-04-14` matched gold on **121/180** (unmodified `goal_scorer.py`). Misses are mostly waive/schedule vs escalate on policy edges, not overlay tools firing. That number is a practice-set smoke, not the hidden 60. On published injection samples the live model sometimes escalates a statement request instead of sending the statement (`c_0168`, sometimes `c_0166`). That is safer than following the paste, and worse than doing the in-policy ask. Idempotency is in memory and dies on restart. Prompt injection is not solved; it is constrained in the tool layer.

**How you would know within an hour.** `/readyz` 503, a burst of 504s, spend-cap hits, `make eval` still green when you know a prompt changed, or no OTLP after `/run`. To turn it off, stop the process (RUNBOOK, Rollback). Two versions can run on different `PORT` / `APP_VERSION` without a rebuild.

**Who pays residual risk.** If we ship the escalate-instead-of-statement behaviour, the customer waits on a human for a statement - ops pays. If we loosen the overlay guard, risk pays when a pasted note moves money. I would pause rollout if eval does not fail under the four gateway regressions, if `/readyz` flaps on good config, or if audit shows a money tool without `verify_identity` on that case.

**Cost of one resolved case.** A tiny synthetic `/run` in the checker is about **$0.00002** on `gpt-4.1-mini-2025-04-14`. A real servicing case is several `complete()` calls. I would budget well under a cent on that snapshot unless a retry loop starts. I have a published match rate (121/180), not a token-median for those 180. The spend cap is the hard stop, not an SLO.
